# 스플렌더 웹게임 기능 요구사항 정의서 v0.1

> 상태: 초안 / 구현 전 검토용  
> 대상 저장소: `limbit95/limbit95.github.io`  
> 기준: Splendor 기본판 핵심 규칙을 웹 멀티플레이 환경에 맞게 구현  
> 주의: 본 문서는 구조와 요구사항만 정의하며 HTML/CSS/JavaScript/SQL 구현은 포함하지 않는다.

---

## 1. 문서 목적

본 문서는 기존 GitHub Pages 사이트 내부에 추가할 **스플렌더 웹게임**의 기능 범위, 게임 규칙, 화면 흐름, 상태 관리, 실시간 동기화, 예외 처리 및 향후 소스 구조를 정의한다.

기존 `liar-game/`과 동일하게 하나의 독립 웹앱 형태로 구성하며, 기존 사이트에서는 게임 목록 또는 링크를 통해 진입하도록 한다.

이번 단계에서는 다음만 확정한다.

- 서비스 범위
- 게임 규칙
- 사용자 흐름
- 게임 상태와 데이터 개념
- 실시간 동기화 원칙
- 향후 디렉터리 및 모듈 구조
- 구현 단계 구분

실제 다음 파일은 아직 생성하지 않는다.

- HTML
- CSS
- JavaScript
- SQL
- 이미지/아이콘 에셋

---

## 2. 서비스 목적

2~4명의 사용자가 각자의 PC 또는 모바일 브라우저로 동일한 게임방에 접속하여 별도 사회자 없이 스플렌더 방식의 게임을 진행할 수 있도록 한다.

웹앱은 다음을 자동 처리한다.

- 게임방 생성 및 참가
- 플레이어 순서 결정
- 인원별 보석 수량 세팅
- 개발 카드 덱 구성 및 공개 카드 관리
- 귀족 타일 구성
- 현재 턴 관리
- 보석 획득 규칙 검증
- 개발 카드 예약
- 개발 카드 구매 가능 여부 및 할인 계산
- 금 토큰 와일드 처리
- 보유 토큰 10개 제한
- 귀족 획득 조건 판정
- 점수 계산
- 15점 이상 도달 시 마지막 라운드 처리
- 최종 승자 및 동점 판정
- 실시간 상태 동기화
- 새로고침/재접속 복구

---

## 3. 기존 프로젝트와의 관계

기존 저장소 구조를 유지하고 스플렌더를 독립 영역으로 추가한다.

예정 경계는 다음과 같다.

```text
/
├─ 기존 사이트
├─ liar-game/
├─ splendor-game/          # 향후 실제 게임 소스
├─ docs/
│  ├─ liar-game/
│  └─ splendor-game/       # 현재 단계에서 먼저 작성
└─ supabase/
   ├─ liar-game/
   └─ splendor-game/       # 향후 DB 산출물
```

스플렌더 앱은 기존 사이트의 SPA 화면 구조와 최대한 분리한다.

재사용 가능한 범위:

- 기존 Supabase 프로젝트
- 기존 Supabase Auth 로그인 세션
- Supabase URL / publishable key 설정

직접 의존하지 않을 범위:

- 기존 SPA Router
- 기존 게시판/활동 기능
- 기존 페이지 렌더러
- 기존 게임의 상태 관리 코드
- 라이어게임 전용 테이블 및 RPC
- 라이어게임 CSS/화면 컴포넌트

---

## 4. 기술 원칙

기존 프로젝트 방향과 동일하게 다음 기술을 기준으로 한다.

- HTML5
- CSS3
- Vanilla JavaScript
- ES Modules
- GitHub Pages
- Supabase Auth
- Supabase PostgreSQL
- Supabase Realtime
- Supabase RPC

사용하지 않는 기술:

- React
- Vue
- Angular
- Next.js
- TypeScript
- npm 기반 빌드 과정
- 별도 Node.js 서버
- 별도 Java/Spring 서버

게임의 권위 있는 상태는 브라우저가 아니라 Supabase DB에 둔다.

---

## 5. 명칭 및 저작권 원칙

개발 단계의 프로젝트명과 폴더명은 `splendor-game`을 사용한다.

공개 서비스 전에는 다음을 별도로 검토한다.

- 최종 표시 게임명
- 공식 로고 사용 여부
- 공식 일러스트 사용 여부
- 공식 카드 디자인 복제 여부
- 공식 카드 데이터의 공개 범위

원칙적으로 공식 이미지와 카드 일러스트를 그대로 복제하지 않고 자체 UI와 그래픽을 사용한다.

---

# 6. 접근 및 플레이어 식별

## 6.1 로그인

기존 사이트의 Supabase Auth 로그인 세션이 존재하는 사용자만 게임에 접근할 수 있도록 한다.

```text
기존 사이트 로그인
    ↓
스플렌더 진입
    ↓
세션 확인
    ↓
게임 로비
```

세션이 없으면 기존 로그인 페이지로 안내한다.

## 6.2 게임 닉네임

게임 표시용 닉네임은 기존 회원 프로필과 분리할 수 있다.

최초 진입 시 게임 닉네임을 입력하거나 이전 게임 닉네임을 재사용한다.

## 6.3 재접속 식별

브라우저에는 최소한 다음 복구 정보만 저장한다.

- player key
- nickname
- current room id 또는 room code

실제 보석, 카드, 점수, 턴 상태는 localStorage에 권위 상태로 저장하지 않는다.

---

# 7. 게임 인원

기본판 기준 플레이 인원은 **2~4명**으로 제한한다.

- 최소 2명
- 최대 4명
- 방장은 최소 2명이 입장한 이후 게임을 시작할 수 있다.
- 게임 시작 후 일반적으로 신규 플레이어의 중도 참가를 허용하지 않는다.
- 진행 중 플레이어 재접속은 허용한다.

---

# 8. 게임방 및 로비

## 8.1 방 생성

방 생성 시 시스템은 다음을 만든다.

- 고유 방 코드
- 방장 플레이어
- 생성 시각
- 방 상태

방 상태 예시:

- `waiting`
- `playing`
- `finished`
- `closed`

## 8.2 방 참가

사용자는 방 코드를 입력해 참가한다.

참가 검증:

- 존재하는 방인지
- 종료/폐쇄된 방인지
- 이미 4명이 참가했는지
- 게임이 이미 시작됐는지
- 동일 사용자가 중복 참가하는지

## 8.3 준비 상태

게임 시작 전 각 참가자는 준비 상태를 변경할 수 있다.

방장은 다음 조건을 만족할 때 게임을 시작한다.

- 참가자 2~4명
- 방장 포함 모든 참가자 준비 완료

---

# 9. 게임 초기 세팅

게임 시작 시 서버가 한 번의 원자적 처리로 초기 상태를 구성한다.

## 9.1 개발 카드

개발 카드는 3개 레벨로 관리한다.

- 1단계
- 2단계
- 3단계

각 레벨의 덱을 독립적으로 섞는다.

게임판에는 각 레벨별로 최대 4장의 카드를 공개한다.

공개 카드가 구매 또는 예약되면 동일 레벨 덱의 다음 카드로 즉시 보충한다.

덱이 소진된 경우 빈 슬롯을 그대로 허용한다.

## 9.2 귀족

게임 인원에 따라 공개 귀족 수를 다르게 한다.

| 인원 | 공개 귀족 |
|---|---:|
| 2명 | 3 |
| 3명 | 4 |
| 4명 | 5 |

## 9.3 일반 보석

일반 보석은 5종으로 관리한다.

- 흰색
- 파란색
- 초록색
- 빨간색
- 검은색

인원별 공급량:

| 인원 | 각 일반 보석 수 |
|---|---:|
| 2명 | 4 |
| 3명 | 5 |
| 4명 | 7 |

## 9.4 금 토큰

금 토큰은 와일드 토큰으로 사용한다.

- 플레이 인원과 관계없이 공급량 5개
- 일반 보석 획득 행동으로 가져갈 수 없음
- 카드 예약 행동 시 공급처에 남아 있다면 1개 획득

## 9.5 선 플레이어

게임 시작 시 선 플레이어를 결정한다.

웹게임에서는 공정성과 단순성을 위해 기본값은 랜덤 선정을 사용한다.

게임 종료까지 턴 순서는 고정된 원형 순서로 진행한다.

---

# 10. 턴 기본 규칙

한 플레이어는 자신의 턴에 **정확히 하나의 주요 행동**을 수행한다.

가능한 행동:

1. 서로 다른 일반 보석 최대 3개 가져오기
2. 같은 색 일반 보석 2개 가져오기
3. 개발 카드 1장 예약하기
4. 개발 카드 1장 구매하기

행동 완료 후 다음 순서로 후처리한다.

```text
주요 행동
  ↓
보유 토큰 10개 제한 처리
  ↓
귀족 조건 확인
  ↓
점수 및 게임 종료 조건 확인
  ↓
다음 플레이어 턴
```

---

# 11. 보석 획득

## 11.1 서로 다른 보석 가져오기

일반 보석 중 서로 다른 색을 최대 3개 선택한다.

- 동일 색 중복 선택 불가
- 금 토큰 선택 불가
- 공급처에 존재하는 색만 선택 가능
- 이용 가능한 일반 보석 색이 3종 미만이면 2개 또는 1개 획득 가능

## 11.2 같은 보석 2개 가져오기

한 색의 일반 보석 2개를 가져온다.

조건:

- 행동 시작 시 해당 색 토큰이 공급처에 최소 4개 존재해야 함
- 금 토큰에는 적용하지 않음

---

# 12. 토큰 보유 제한

플레이어는 턴 진행 도중 10개를 초과하여 토큰을 가질 수 있다.

그러나 턴 종료 전에는 반드시 총 토큰을 **10개 이하**로 맞춰야 한다.

토큰 수 계산에는 다음을 포함한다.

- 일반 보석 토큰
- 금 토큰

개발 카드 보너스는 포함하지 않는다.

초과 시 UI에서 반납할 토큰을 선택하게 하고, 10개 이하가 되기 전에는 턴을 완료할 수 없다.

---

# 13. 개발 카드 예약

플레이어는 다음 중 하나의 카드를 예약할 수 있다.

- 현재 공개된 개발 카드
- 선택한 레벨 덱의 맨 위 비공개 카드

예약 규칙:

- 플레이어당 최대 3장
- 예약된 카드는 해당 플레이어만 구매 가능
- 예약 카드를 임의로 버릴 수 없음
- 공개 카드를 예약하면 해당 슬롯을 즉시 같은 레벨의 다음 카드로 보충
- 공급처에 금 토큰이 있으면 예약과 동시에 금 토큰 1개 획득
- 금 토큰이 없어도 예약 행동은 가능

비공개 덱에서 예약한 카드는 예약한 플레이어에게만 카드 정보를 공개한다.

---

# 14. 개발 카드 구매

플레이어는 다음 중 1장을 구매할 수 있다.

- 게임판의 공개 카드
- 자신의 예약 카드

구매 가능 여부는 다음 공식으로 판단한다.

```text
실제 필요 수량 = max(카드 비용 - 보유 영구 보너스, 0)
```

부족한 일반 보석은 금 토큰으로 대체할 수 있다.

구매 시:

- 사용한 일반 토큰은 공급처로 반환
- 사용한 금 토큰도 공급처로 반환
- 구매한 개발 카드는 플레이어 소유가 됨
- 카드의 보석 색은 영구 보너스 1개로 누적
- 카드에 점수가 있다면 즉시 플레이어 점수에 반영

영구 보너스가 비용 이상이라면 토큰을 사용하지 않고 구매할 수 있다.

---

# 15. 개발 카드 보너스

구매한 개발 카드는 카드 색과 같은 영구 보너스를 제공한다.

보너스는 소모되지 않는다.

예:

```text
빨간 카드 3장 보유
→ 이후 모든 카드 구매에서 빨간 비용 3 할인
```

화면에는 플레이어별로 각 색의 보너스 개수를 항상 확인할 수 있어야 한다.

---

# 16. 귀족 획득

주요 행동과 토큰 반납 처리가 완료된 후 귀족 획득 조건을 확인한다.

귀족 조건은 플레이어의 **개발 카드 영구 보너스 수량**으로만 계산한다.

실제 보석 토큰과 금 토큰은 귀족 조건에 포함되지 않는다.

조건을 충족한 귀족이 1명이라면 자동 획득한다.

동시에 2명 이상의 귀족 조건을 충족한 경우 플레이어가 그중 하나를 선택한다.

한 턴에 획득 가능한 귀족은 최대 1개다.

귀족 획득은 주요 행동으로 계산하지 않는다.

---

# 17. 점수

플레이어 점수는 다음 합계다.

```text
구매한 개발 카드의 명성 점수
+
획득한 귀족 점수
```

점수는 모든 플레이어에게 공개한다.

---

# 18. 게임 종료

플레이어가 자신의 턴 종료 시 **15점 이상**이 되면 게임 종료 라운드를 발동한다.

즉시 게임을 끝내지 않고 모든 플레이어가 같은 수의 턴을 수행하도록 현재 라운드 끝까지 진행한다.

예:

```text
턴 순서 A → B → C → D

B가 15점 도달
→ C 턴
→ D 턴
→ 게임 종료
```

선 플레이어의 바로 이전 순서 플레이어가 마지막 턴을 가진다.

## 18.1 승리 판정

1. 최종 명성 점수가 높은 플레이어 우승
2. 점수가 같으면 구매한 개발 카드 수가 더 적은 플레이어 우승
3. 개발 카드 수까지 같으면 공동 우승

---

# 19. 실시간 멀티플레이

모든 클라이언트는 같은 게임 상태를 확인해야 한다.

실시간으로 동기화해야 하는 핵심 정보:

- 현재 플레이어
- 공급처 보석 수량
- 공개 개발 카드
- 개발 카드 덱 잔여량
- 공개 귀족
- 각 플레이어의 점수
- 각 플레이어의 영구 보너스
- 각 플레이어의 공개 토큰 수량
- 각 플레이어의 예약 카드 장수
- 자신의 예약 카드 상세
- 마지막 행동 로그
- 게임 종료 상태

다른 플레이어의 비공개 예약 카드 내용은 노출하지 않는다.

---

# 20. 서버 권위 및 동시성

브라우저는 행동 가능 여부를 미리 안내할 수 있으나 최종 검증은 DB/RPC가 수행한다.

다음 작업은 반드시 현재 턴과 게임 버전을 검증한다.

- 토큰 획득
- 토큰 반납
- 카드 예약
- 카드 구매
- 귀족 선택
- 턴 종료

중복 클릭이나 네트워크 재전송으로 동일 행동이 두 번 처리되지 않아야 한다.

한 턴의 상태 변경은 가능한 한 원자적으로 처리한다.

---

# 21. 재접속 및 새로고침

게임 도중 새로고침 또는 일시적인 네트워크 단절이 발생해도 기존 플레이어로 복구할 수 있어야 한다.

복구 시 서버에서 최신 snapshot을 다시 읽는다.

복구 대상:

- 방
- 플레이어
- 현재 게임
- 현재 턴
- 보석 공급처
- 카드 상태
- 자신의 예약 카드
- 귀족
- 점수
- 게임 종료 여부

localStorage 데이터만으로 게임 상태를 복원하지 않는다.

---

# 22. 플레이어 이탈

게임 시작 전:

- 자유롭게 방 나가기 가능
- 방장이 나가면 방장 위임 또는 방 폐쇄 정책 필요

게임 시작 후:

- 단순 연결 끊김과 명시적 게임 포기를 구분한다.
- 일시적 연결 끊김은 재접속을 기다린다.
- 포기 기능을 제공할 경우 게임 전체 처리 정책을 별도 확정해야 한다.

v0.1에서는 **게임 중 포기/강제 퇴장 규칙은 구현 확정 전 추가 논의 항목**으로 둔다.

---

# 23. 화면 요구사항

최소 화면 상태는 다음과 같다.

1. 접근 검사
2. 닉네임 설정
3. 게임 로비
4. 방 생성/참가
5. 대기방
6. 메인 게임판
7. 토큰 초과 반납 선택
8. 복수 귀족 선택
9. 게임 결과
10. 연결 복구/오류 상태

메인 게임판에서는 최소한 다음 정보가 한 화면 안에서 구분되어야 한다.

- 귀족 영역
- 3단계 개발 카드
- 2단계 개발 카드
- 1단계 개발 카드
- 중앙 보석 공급처
- 현재 턴
- 내 보유 토큰
- 내 영구 보너스
- 내 예약 카드
- 상대 플레이어 요약
- 현재 점수

PC와 모바일 모두 플레이 가능하도록 반응형 UI를 고려한다.

---

# 24. 행동 로그

최근 게임 행동을 간단한 공개 로그로 보여줄 수 있다.

예:

- `성혁님이 빨강/파랑/초록 보석을 가져갔습니다.`
- `예진님이 2단계 카드를 예약했습니다.`
- `민수님이 개발 카드를 구매해 2점을 획득했습니다.`
- `은주님이 귀족의 방문을 받아 3점을 획득했습니다.`

비공개 예약 카드의 상세 정보는 로그에 노출하지 않는다.

---

# 25. 오류 및 예외 처리

최소한 다음 오류를 사용자에게 명확히 안내한다.

- 내 턴이 아님
- 이미 처리된 턴
- 선택한 보석이 부족함
- 같은 색 2개 획득 조건 불충족
- 보석 선택 규칙 위반
- 예약 카드 3장 초과
- 대상 카드가 이미 다른 플레이어에 의해 사라짐
- 카드 구매 비용 부족
- 잘못된 예약 카드 접근
- 보유 토큰 10개 초과 상태 미처리
- 귀족 선택 필요
- 로그인 세션 만료
- 방 만료/종료
- 네트워크 오류
- 실시간 연결 해제

오류 발생 시 클라이언트는 임의 상태를 유지하지 않고 최신 snapshot 재조회가 가능해야 한다.

---

# 26. 보안 요구사항

- 클라이언트에는 Supabase publishable/anon key만 사용한다.
- `service_role` key를 브라우저에 사용하지 않는다.
- 게임 상태 변경은 인증된 사용자만 가능하다.
- 사용자가 참여하지 않은 방의 비공개 정보에 접근할 수 없어야 한다.
- 상대 플레이어 예약 카드의 내용은 서버 응답 단계에서 숨긴다.
- 클라이언트가 임의의 점수, 보석, 카드 상태를 직접 갱신할 수 없도록 한다.
- 주요 mutation은 RPC 중심으로 구성한다.

# 30. 개발 진행 원칙

이 프로젝트의 변경은 다음 절차로 진행한다.

```text
요구사항/구조 설계
    ↓
변경 내용 요약 보고
    ↓
사용자 검토
    ↓
사용자가 "반영하자" 승인
    ↓
main 브랜치 반영
```

사용자 승인 이전에는 설계 브랜치 또는 작업 브랜치에서만 변경하며 `main`에 머지하지 않는다.
