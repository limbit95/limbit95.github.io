# Splendor Phase 5 — 공개 카드 예약

## 범위

Phase 5에서는 카드 구매보다 먼저 **공개되어 있는 개발 카드 예약**만 실제 서버 기능으로 연결한다.

포함 기능:

- 현재 턴 플레이어만 공개 카드 예약 가능
- 예약 카드 최대 3장
- 예약한 카드는 공개 자리에서 제거
- 같은 티어 덱에 카드가 남아 있으면 같은 슬롯에 즉시 보충
- 공급처에 금 토큰이 남아 있으면 예약 시 금 1개 획득
- 금 토큰이 없어도 예약 자체는 가능
- 금 획득으로 토큰이 10개를 넘으면 기존 `return_excess` 단계 사용
- 예약이 정상 종료되면 다음 플레이어로 턴 이동
- game version 증가 및 기존 private Broadcast로 실시간 동기화
- client action id 기반 중복 요청 방지
- 예약 카드의 정체는 예약한 본인의 Snapshot에만 포함
- 상대방에게는 예약 카드 장수만 노출

이번 Phase에는 다음 기능을 포함하지 않는다.

- 덱 맨 위 카드를 뒷면으로 예약
- 예약 카드 구매
- 공개 카드 즉시 구매
- 영구 보너스 할인 계산
- 금 토큰을 와일드카드로 사용하는 결제

## 적용 규칙

### 공개 카드 예약

현재 자신의 턴이고 `turn_phase = action`일 때 공개 카드 1장을 예약할 수 있다.

예약된 카드는 다음 상태가 된다.

- `location = reserved`
- `face_up_slot = null`
- `owner_game_player_id = 예약한 플레이어`
- `reserved_hidden = false`

플레이어의 `reserved_card_count`는 1 증가한다.

### 예약 한도

`max_reserved` 기본값은 3이다.

이미 3장을 예약한 플레이어가 추가 예약을 시도하면 서버에서 `RESERVE_LIMIT_REACHED`로 거부한다.

### 금 토큰

예약 시 공급처에 금 토큰이 1개 이상 있으면:

- 공급처 금 -1
- 플레이어 금 +1

금 토큰이 0개라면 금을 받지 못하지만 카드 예약은 정상 진행한다.

### 공개 카드 보충

예약한 카드의 기존 `tier`와 `face_up_slot`을 기억한다.

같은 티어의 `deck` 카드 중 다음 순서의 카드가 있으면 그 카드를 기존 슬롯에 `face_up`으로 이동한다.

덱이 완전히 소진된 경우에는 해당 슬롯이 빈 상태로 남는다.

### 토큰 10개 제한과 연결

예약으로 금 토큰을 받아 보유 토큰이 10개를 초과하면:

1. 예약과 카드 보충은 완료한다.
2. 금 토큰도 획득한다.
3. 현재 턴은 유지한다.
4. `turn_phase = return_excess`가 된다.
5. 기존 Phase 4 반환 UI에서 필요한 개수만큼 반환한다.
6. 반환이 끝난 뒤 다음 플레이어에게 턴이 넘어간다.

## 서버 RPC

`public.splendor_reserve_faceup`

입력:

- `p_room_id`
- `p_card_instance_id`
- `p_expected_version`
- `p_client_action_id`

서버에서 다시 검증하는 항목:

1. 로그인 및 승인 회원 여부
2. 현재 방 참가자 여부
3. 진행 중인 게임 여부
4. client action id 중복 여부
5. expected game version
6. `turn_phase = action`
7. 현재 턴 플레이어 여부
8. 예약 카드 3장 제한
9. 선택 카드가 현재 실제 공개 카드인지

## 예약 카드 정보 보호

`private.splendor_game_snapshot()`에 `reserved_cards`를 추가했다.

하지만 이 배열은 `(auth.uid())`와 `owner_game_player_id`가 연결된 **자신의 예약 카드만** 반환한다.

공용 `players` 배열에는 기존과 같이 `reserved_card_count`만 포함한다.

따라서 다른 플레이어는:

- 상대가 예약 카드 몇 장을 갖고 있는지 확인 가능
- 상대 예약 카드의 카드 ID/이름/비용/보너스는 Snapshot으로 받을 수 없음

## 자동 검증 결과

모든 테스트는 실제 진행 게임을 사용하되 `BEGIN ... ROLLBACK` 안에서 실행하여 사용자 게임 데이터를 보존했다.

### 일반 예약

토큰을 여유 있게 만든 테스트 상황에서 공개 카드 예약:

- 예약 카드 수 0 → 1
- 금 토큰 0 → 1
- 공급처 금 5 → 4
- 공개 카드 총 12장 유지
- 선택 카드와 같은 티어 덱 6 → 5
- game version 9 → 10
- turn 10 → 11
- 다음 플레이어에게 턴 이동

### 토큰 10개 상태에서 예약

이미 토큰 10개를 보유한 상황에서 예약:

- 예약 완료
- 금 1개 획득
- 총 토큰 11개
- `turn_phase = return_excess`
- `must_return_count = 1`
- 현재 플레이어 턴 유지
- 공개 카드 보충 완료

### 금 토큰 없음

공급처 금을 0으로 만든 테스트 상황:

- 카드 예약 정상 성공
- 금 획득 없음
- 다음 플레이어로 턴 이동

### 중복 요청

동일 `client_action_id`로 같은 예약 RPC를 두 번 호출:

- 실제 예약 1회만 적용
- 금 1개만 지급
- game version 1회만 증가
- action log 1건만 기록

### 예약 한도

`reserved_card_count = 3`인 테스트 상황에서 추가 예약:

- `RESERVE_LIMIT_REACHED`로 서버 거부

### 상대방 정보 보호

A가 카드를 예약한 후 B의 Snapshot을 조회:

- B의 `reserved_cards` 배열: 0장
- 공용 플레이어 정보에서 A의 `reserved_card_count`: 1장
- 공개 카드: 새 카드가 보충되어 12장 유지

### 테스트 데이터 보존 확인

모든 rollback 테스트 종료 후 실제 진행 게임을 재확인:

- game version 기존 값 유지
- turn 기존 값 유지
- 실제 reserved 카드 0장 유지
- 실제 `reserve_faceup` action log 0건 유지

## 사용자 테스트 체크리스트

스플렌더 규칙을 몰라도 아래 결과만 확인하면 된다.

1. **현재 턴인 사람**이 공개 카드 하나를 클릭한다.
2. 오른쪽 `선택한 카드` 영역의 **`이 카드 예약하기`** 버튼이 활성화되는지 본다.
3. 예약 버튼을 누른다.
4. 선택한 카드가 공개 카드 줄에서 빠지고 **같은 단계의 새 카드가 그 자리를 채우는지** 확인한다.
5. 오른쪽 **`내 예약 카드`**에 방금 카드가 나타나는지 확인한다.
6. 내 예약 수가 `0 → 1`로 증가하는지 확인한다.
7. 금 토큰이 남아 있었다면 **공급처 금 -1 / 내 금 +1** 되는지 확인한다.
8. 토큰이 10개 이하라면 상대방에게 턴이 넘어가는지 확인한다.
9. 상대방 브라우저에서도 공개 카드와 턴이 자동으로 똑같이 바뀌는지 확인한다.
10. 상대방 화면에서는 내 예약 카드의 **내용이 아니라 예약 장수만** 보이는지 확인한다.

### 현재 실제 테스트 게임에서 예상되는 특수 흐름

Phase 4 테스트 결과 현재 플레이어들이 토큰을 많이 보유한 상태일 수 있다.

현재 턴 플레이어가 이미 토큰 10개를 가지고 있고 공급처에 금이 남아 있다면 예약 직후 정상 결과는:

- 카드 예약 성공
- 금 1개 획득
- 토큰 총 11개
- **턴이 바로 넘어가지 않음**
- `토큰 1개를 반환해 주세요` 화면 표시
- 원하는 토큰 1개 반환
- 총 토큰 10개
- 그 다음 상대방에게 턴 이동

이 흐름이 나타나는 것은 오류가 아니라 정상 규칙이다.
