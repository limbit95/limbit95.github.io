## 3. 3A — 허용 의존과 금지 규칙

- 구성 진입점은 Profile의 선언을 읽어 Core·선택 모델·Capability·Game-local·Site Adapter의 계약을 연결한다. Profile 자체가 모든 구현을 상속·소유하지 않는다.
- 선택 모델/Capability는 필요한 Core 공통 계약과 **명시된 상대 계약**을 소비할 수 있다. 게임 연결 코드도 이 계약을 소비한다. 공통 구현은 특정 게임의 폴더·상태 구조·상수·UI를 역으로 import하지 않는다.
- Core는 특정 게임·사이트·선택 모델 구현에 역의존하지 않는다. 인터페이스/주입된 동작을 호출하는 것과 특정 구현에 의존하는 것은 구분한다. Site Adapter 구현은 사이트 서비스와 경계 계약을 연결하고 Core 안으로 사이트 전역을 밀어 넣지 않는다.
- 모델 간 협업은 필요한 관계를 명시한다. 상호 내부 상태 접근, 숨은 전역 currentRoom/currentMatch, 양쪽이 동시에 동일한 resource의 최종 파괴권을 갖는 구조는 금지한다. callback만으로 순환 의존을 숨기지 않는다.
- Game-local/Capability/장르 규칙은 공통 수명·권한·안전성 의무를 낮출 수 없다. 선택 불가/의미 불일치는 새 모델 계약 검토로 돌리고 fake method나 workaround로 통과시키지 않는다.
- 현행 snapshot adapter와 새 모델은 계약 경계에서 공존한다. 현행 public API/import/DB·규칙·UI를 변경해 강제 이관하지 않는다. 실제 Adapter 필요/그대로 연결/새 구현/local/보류는 5A에서 판정한다.

이 규칙은 논리 의존 초안이다. 실제 모듈 경로·package·파일 분리·계약 version은 6의 책임이다.

## 6. 3B — 늦은 완료 채택과 정리

### 6.1 채택 조건

반영 대상마다 다음 의미를 모두 충족해야 한다. 한 숫자 version 또는 callback 입구의 disposed 검사 하나로 축약하지 않는다. 이는 API/알고리즘 동결이 아닌 안전성 조건이다. (E10/16/22~27 및 원문검토 S01~07)

1. **살아 있는 반영 대상:** 대상 실행/소비자와 그 작업의 소유 수명이 유효하다. 종료된 실행의 결과로 새 실행을 건드리지 않는다.
2. **현재 맥락에 적용 가능:** 결과의 대상·경기·tracking·viewer 맥락이 현재 반영 범위와 맞음을 선택 모델이 설명한다. 적용되지 않는 차원은 근거와 함께 제외하며 fake Room을 만들지 않는다.
3. **허용 정보/행위:** 현재 소비자가 사용할 수 있는 정보여야 한다. client 검사는 server의 권한 집행을 대체하지 않는다. 권한 근거가 미확정이면 private 사용을 보류한다.
4. **모델 안의 순서:** 비교 가능한 범위에서 stale/중복/확정 여부를 모델 계약에 따라 판단한다. 같은 version·더 큰 version도 다른 수명/권한의 결과를 살리지 못한다. 상세 ordering/중복 규칙은 4B다.
5. **반영 시점 유지:** 검사와 상태·cache·연출·오류·후속 작업 반영 사이에 await 또는 맥락 변경 가능성이 있으면 반영 직전 다시 확인하거나 동등한 일관성 근거가 필요하다. 재진입 callback도 고려한다.

발행 시각이 오래됐다는 사실만으로 모든 데이터를 버리지는 않는다. 이전에 시작된 재조회가 **현재 맥락의 authoritative·authorized 상태**를 실제 반환했고 현재 소비자가 이를 검증할 근거가 있으면 새 맥락의 입력으로 채택할 수 있다. 이전 작업의 생존을 인정하는 것이 아니라 현재 소비자의 명시적 재검증이다. payload의 room 이름만 덮어씌우는 방식은 근거가 아니다. 입증할 수 없으면 거부하고 현재 맥락으로 재조회한다. 전환을 승인하는 현재 제어 흐름과 전환 이전 작업의 늦은 완료를 구분해야 하므로 단순히 모든 경계 불일치 결과를 전역 폐기하는 구현도 확정하지 않는다.

| 완료 경로 | 적용 판단 |
|---|---|
| 성공/snapshot | 모든 조건을 통과한 상태만 반영. action 직접 응답과 구독/refresh를 동일한 의미로 다룸 |
| error | 과거 맥락 오류가 현재 오류/연결 상태·toast·복구·로그의 private 정보 사용을 유발하지 않음. 현재 오류와 별도로 안전한 과거 작업 진단을 남기는 것은 가능 |
| null/없음 | 단순 무해 값이 아님. 현재 대상의 부재임을 검증한 경우에만 현재 화면/추적을 비움. 과거 조회 null은 현재 상태 삭제 근거가 아님 |
| finally | 이전 작업 소유의 bookkeeping/resource 정리는 가능. 새 작업 busy·inFlight·spinner·connection을 해제하지 않음 |
| cleanup/leave 완료 | 이전 owner의 자원만 해제. 현재 owner의 구독·룸·화면을 정리하지 않음. 이미 server에 commit된 leave가 client 거부로 rollback되지는 않음 |
| effect/후속 비동기 작업 | 결과 연출·sound·타이머·재조회 예약도 같은 적용 조건. 허용되지 않는 결과로 다음 작업을 시작하지 않음 |

### 6.2 dispose와 자원 소유 판단

**취소 요청, 실제 중단, 채택 무효화, 자원 정리는 서로 다른 사실**이다. 공통 계약은 취소 성공에 의존하지 않는 무효화를 요구한다. 모델별 transport가 취소를 지원하면 활용할 수 있지만 안전성 전제는 아니다.

- 종료 경계에서는 먼저 해당 수명의 반영 권리를 무효화한다. 정리 중 오류·재진입·늦은 완료가 생겨도 되살아나지 않아야 한다. 종료 상태와 자원 해제 완료/실패 상태를 구분한다.
- 반복 dispose의 **관찰 가능한 의미는 반복 안전**해야 한다. 이미 완료된 해제는 재실행하지 않거나 안전한 방식으로 처리한다. 개별 외부 API가 멱등이라는 가정으로 전가하지 않는다. 종료 실패가 발생했다고 새 작업 채택을 허용하지 않는다.
- 부분 초기화에서 실제 획득한 자원만 정리하며, 한 자원 정리 실패가 독립 자원 정리 시도 전체를 막지 않도록 한다. 의존하는 자원은 필요한 순서를 지키고 실패를 기록한다. 성공하지 않은 cleanup을 완료로 표시하지 않는다. 재시도·timeout·오류 집계 API는 미결정이다.
- dispose 후 비동기로 자원을 얻으면 이전 owner가 즉시 해제/격리할 책임이 있다. 새 실행에 자동 부착하지 않는다. 늦은 정리도 새 실행을 조회하는 mutable 전역 대신 자신에게 귀속된 자원을 대상으로 한다.
- DOM의 같은 target/type/callback/capture를 재사용하는 경우 이전 remove가 새 등록을 없앨 수 있다. 수명별 callback/등록 handle 또는 동등한 소유 확인이 필요하다. 특정 방식은 5A/6에서 정한다.
- 사이트 공용 BGM/연결 같은 공유 자원은 명시된 공용 owner가 소유한다. 게임 수명 종료는 자신의 사용권만 반납하며 공용 자원을 임의 파괴하지 않는다. 참조 계수나 lease API를 지금 고정하지 않는다.
- stop/pause, detach, dispose, 서버 경기 종료를 혼동하지 않는다. 재개 가능한 stop의 의미와 영구 종료의 의미는 모델 계약으로 명시한다. 기존 함수 이름만으로 동일한 보장을 가정하지 않는다.

T03은 권한 감소·로그아웃·사용자 변경을 인지하면 이전 private 정보의 현재 사용을 우선 차단하고 새 view의 근거를 확인한다. public 부분 재사용도 분리와 현재 권한 근거가 있어야 한다. 이미 적법하게 전달된 비밀을 악의적인 client에서 회수할 수 있다고 약속하지 않는다. 미인지 철회, 이미 전송 중인 정보, 서버 검사 시점·전파 지연·캐시 키는 4B에서 명시할 보안 경계이며 현재 안전 지원 판정은 보류다.

## 8. 기존 구현·새 모델 공존과 반례

**기준 사실(E22~27):** coordinator는 load 이후 version을 검사하며 낮은 값만 거부하고 동등값은 허용한다. await 직후 disposed를 다시 확인하지 않으며 catch/finally가 별도 실행된다. stop은 구독을 정리하지만 진행 중 promise 완료를 차단하는 증거가 아니다. Can’t Stop은 action 결과 직접 apply와 coordinator 경로가 공존한다. No Thanks!는 일부 callback에 generation/room/disposed 검사를 갖지만 같은 Room 재사용이 Match/view 교체를 구분한다는 증거는 없고 일반 command catch/finally는 같은 보호를 모두 공유하지 않는다. Reconnect의 listener stop도 이미 시작한 refresh 완료 취소와 다르다.

**판단:** 기존 일부 방어를 공통 보장으로 승격할 수 없다. STEP1 F01/IMPL001·002·004·005 및 승인 T01~03의 보장 부족을 구체 채택 조건으로 연결했다. 새로 런타임 결함을 재현했다거나 기존 게임 수정 완료라고 주장하지 않는다. 5A는 각 경로가 §6을 충족하는지 확인한 뒤 재사용/Adapter/새 구현/local/보류를 선택해야 한다. 현재 코드는 그대로 둔다.

## 9. 충돌·회귀·후속 미결정

**3A↔3B 충돌 검토:** Core가 공통 유효 수명 의무를 소유하고 모델이 맥락 의미를 제공하며 소비자가 반영을 집행하는 배정으로 T01~03을 설명할 수 있다. viewer 경계는 보편 관전 기능을 추가한 것이 아니라 권한/정보 범위가 바뀌는 모델의 적용 조건이다. cleanup 안전성은 계획의 기존 공통 정리 의무를 구체화한 것이다. Core에 Room/host/DB/단일 tick/글로벌 current state/새 필수 필드를 추가하지 않았다.

**회귀 판단:** 새 필수 Core 전제 미발견, STEP2 즉시 회귀 불필요. 이는 승인 STEP3 판단과 일치한다. 후속 설계에서 선택표7축으로 표현 불가, 공통 수명 안전성 누락, 모든 게임에 새로운 전제 필요, hostless/비DB 의무를 면제해야만 성립하는 경우에는 STEP2 및 관련 규칙 판단을 다시 검토한다. 현행 §6과 §10B의 적용 조건은 합쳐 지우지 않는다. STEP3 S3-R01~07은 해결 완료로 닫지 않는다.
