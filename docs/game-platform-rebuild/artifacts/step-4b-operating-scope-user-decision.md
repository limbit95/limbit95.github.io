## 채택한 사용자 결정

사용자가 이번 요청에서 [CP0071](../checkpoints/CP-0071-step-4b-binding-adoption-judgment.md)의 [선택1 추천안](step-4b-binding-adoption-judgment.md)을 명시적으로 채택했다. **실제 보장 범위 변경**이며, 이전 요구와 동일한 설명 정리가 아니다. 누적 결정 [D-0008](../DECISIONS.md)에 기록한다.

| 구분 | 채택 내용 |
|---|---|
| 외부 철회5초 | 외부 Auth 철회의 실제 효력 R부터 대상 session의 보호 행동 반영 C·새 정보 제공 P를 최대5초 내 차단하는 기준을 명시된 운영 장애 범위에 적용 |
| 유지되는 일반 장애 | 정상 실행, 일반 지연·통신 단절·이벤트 유실은 권한 재검증과 실패 시 차단 대상으로 유지. 이를 일괄 예외로 분류하지 않음 |
| 정지 한계와 수용 위험 | 최종 검사 이후 runtime·DB·host가 장시간 정지한 경우까지 예외 없이5초 내 실제 C/P 차단을 보장하지 않음. 이미 마지막 검사를 지난 행동/정보 제공이 늦게 완료될 잔여 위험을 수용 |
| 재개 | 새 작업을 닫고 현재 권한 재검증. 이미 진행 중인 작업까지 반드시 회수하거나 재개 뒤 추가 완료0을 약속하지 않음 |
| 다른 deadline에 미치는 한계 | 같은 물리적 정지 한계가 known expiry·인지한 권한 실패·장애60초 집행에도 영향을 줄 수 있음을 명시. 그 경우까지 절대시간 실행 보장을 주장하지 않음 |
| 계속 금지 | 의도적인 만료 유예, 실패 인지 뒤 추가 허가, 처음부터 무권한인 접근의 허가 발급, 사후 예외 확대,5초의 percentile 전환 |
| 설계 잔여 | 운영 장애 범위의 정확한 기술적 경계와 검증 조건은 후속 Astra 판단에서 확정. 이번에 새 수치/예외 목록/주기/제품/알고리즘을 정하지 않음 |

외부 철회5초·정상망 회복 후 각 재연결5초·최초 권한 장애60초는 별개다. P는 서버가 통제하는 최종 취소 불가 transport 인계이며 그 뒤 OS/TLS/network 지연 전달·재전송의 회수 미보장은 D0007 그대로다. 취소 가능한 app queue나 snapshot 생성으로 P를 앞당기지 않는다. 통제 가능한 사이트 내부 승인/역할 변경의 DB 순서 보호, 최초 무권한 차단, 중복/owner·현재 권한/삭제·복원 보호도 유지한다.

## 대체 관계와 현재 상태

- D0006 설계 승인/실행·오픈 검증 분리는 그대로 유지한다.
- D0007 중 예외 없는 최종5초 상한과 after-check 정지 후 late C/P 불허 해석을 위 범위에서 대체한다. known expiry·인지 실패·60초에도 동일 정지 한계를 명시한다. 새 의도적 유예 정책은 아니다.
- D0007 원문과 CP0067~71은 당시 이력으로 보존하며 삭제/재작성하지 않는다. 현재 판단은 D0007과 그 부분 대체 결정 D0008을 함께 읽는다.
- CP0071 최상위 C는 당시 예외 없는 기준에 대한 판정이다. 정책이 바뀌었다고 과거 판정을 A로 고치지 않는다. 변경 기준의 후보 채택 가능 여부는 Astra가 새로 판단할 일이다.
- 사용자 정책 선택은 완료. **후보 설계 승인·G03/STEP4B 완료·구현/오픈 승인은 미완료**. 구조적 공백은 나중 시험으로 대신하지 않는다. 실행 NOT_RUN만으로 설계 전체를 자동 HOLD하지도 않는다.
