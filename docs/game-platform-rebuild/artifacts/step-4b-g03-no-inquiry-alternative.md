# STEP4B — 공급자 문의 없는 G03 대안 판정 (CP0065)

2026-10-06 KST. 입력 CP0064 `5d2424405410696db4afd44d439d9a5210f04f80`; 시작 PR412 HEAD 일치/추가 변경 0. 사용자의 “굳이 문의?” 및 문의 없이 대안 판단 추천에 대한 “진행하자”를 이번 범위로 적용한다. 대안 설계 판단/기록 제출 허용이며 운영 Auth 교체·정책 완화·구현 승인으로 확대하지 않는다. CP0064의 문의 우선 작업 순서만 아래 순서로 대체하며 과거 문서는 당시 이력으로 보존한다.

## 판정과 추천 하나

**추천 구조: 통제된 권한·철회 집행 계층 + DB 권위 + 단일 최종 송신 경계.** 공급자 내부 writer가 최종 송신을 통제해 줄 것이라는 미확인 계약을 채택 전제로 삼지 않고, 실제 R/C/P에 영향을 주는 writer와 실행 주체를 우리가 통제할 수 있는 구조로 바꾸는 대안이다. 별도 장르 플랫폼이 아니라 기존 통합 플랫폼의 Site Adapter/Authority 책임 범위에서 검토한다. 저빈도 DB 우선 및 A안 안전성을 유지한다.

**설계상 필요조건은 판단 가능, 운영 구성 채택은 HOLD.** 직접 통제는 분산 원자성·OS queue·만료·장애를 자동 해결하지 않는다. 따라서 “문의 없이 바로 보장 가능한 완성안”이라고 주장하지 않는다. 현재 managed Auth를 그대로 유지한 채 모든 직접 Auth R에 즉시 연동하는 충족 구조는 확보되지 않았다. 공급자 비지원 또는 기술 전반 불가능을 확인했다는 뜻도 아니다.

후보를 더 늘리지 않는다. 이번 수용 심사의 결론은 **현재 근거로는 운영 구조를 채택할 수 없고, 문의 없이 진행할 설계 방향만 제안할 수 있다**는 것이다. 수용 불가이면 G03 목표와 현재 구성의 충돌로 명시하고 멈춘다. 다시 공급자 문의 또는 같은 자료 수집을 필수 선행 단계로 돌리지 않는다.

## 구체적인 권위 구조

| 구성/책임 | 설계 권고 | 반드시 남는 경계 |
|---|---|---|
| 권한·철회 집행 계층 | 승인·가입·역할·permission·session 상태·scope별 logout·계정 삭제의 모든 권위 변경을 추적 가능한 한 순서로 집행. 접근 차단의 의도를 먼저 내구화하고 진행 중 C/P를 차단하는 절차를 연결 | 서로 독립적인 DB/외부 두 write를 원자적이라고 가정하지 않음. 부분 실패는 보호 서비스 닫힘, 완료 응답 금지 |
| DB 권위 | command binding/dedupe·판 lifecycle·저빈도 authoritative mutation·terminal·인가 revision/incarnation/owner 조건은 DB가 완결 가능한 범위에서 commit | 외부 simulation이 새로운 권위 결정을 하면 그것도 C이며 동일 철회 순서에 참여. DB allow 후 독립 apply 배제 유지 |
| 외부 실행 | 권위 계층이 확정한 실행 범위만 처리. worker는 보호 payload를 사용자에게 직접 송신할 권한/경로를 갖지 않는 설계를 목표로 함 | 네트워크 분리·credentials·배포/privileged 우회까지 실제 설정/시험 필요. 문서로 direct socket이 없어졌다고 선언하지 않음 |
| 단일 최종 송신 경계 | recipient/session/view/revision/payload와 incarnation/owner를 묶어 최종 제공. snapshot·duplicate ack·retry/error·재연결·늦은 callback 모두 같은 경로 사용 | 조회한 allow를 따로 보관해 쓰는 gateway는 불충분. 실제 egress를 차단하는 위치와 queue/transport의 보장 필요 |
| 복원 개방 | 격리 복원·새 incarnation·옛 owner/session 무효화·현재 권한/삭제 원천 확인 이후에만 보호 경계 개방 | 복원된 epoch/승인 상태를 현재 원천으로 재사용 금지. 독립 원천도 rollback되면 닫힘 유지 |

실행 순서 후보는 **닫기/진행 작업 배제 → old owner/보호 queue 차단 확인 → 해당 변경의 권위 commit/최종 응답**이다. 완료가 확인되지 않으면 보호 service를 닫고 변경의 성공을 응답하지 않는다. 이는 통제 가능한 변경 요청에 대한 절차이며 이미 별도로 효력을 얻은 managed R을 나중으로 재정의하는 수단이 아니다. 권한 변경이 실패해도 추가 차단을 유지하는 것은 가능하지만 철회 성공을 꾸며낼 수 없다.

**만료는 요청형 철회와 다르다.** exp/not_after 등 기존 효력 deadline을 미룰 수 없다. app process가 멈춰도 deadline 이후 실제 C/P가 나오지 않도록 최종 집행 경계가 독립적으로 유효기간을 집행해야 한다. 짧은 TTL·wall-clock 조회·event-loop timer만으로 보장하지 않는다. 정확한 runtime/OS/transport와 deadline 오차·queue 취소 의미는 미선택/실행 증거 부족으로 HOLD다. lease를 갱신했다는 사실만으로 이 경계를 닫지 않는다.

DB 연결이 끊긴 old process가 재개해도 직접 effect/send 경로가 없거나 최종 집행기가 현재 owner를 거절해야 한다. 최종 집행기 자체의 old instance·partition·OS buffer에도 같은 의무가 적용된다. DB CAS로 저장 deny만 확인하는 것은 송신 차단 증거가 아니다. 다수 owner가 필요해지는 제품을 자동 채택하지 않고, 초기 설계는 동시 보호 집행 owner 하나와 검증된 차단 후 인수 조건을 우선한다. 실제 가용성/성능은 미검증이다.

| 철회 writer 직접 통제 | vNext 보호 권한에 효력을 주는 Auth/권한 경계를 직접 운영/통제하는 방향 | 사이트 Auth 변경/대체·session 연결·운영권한 통제가 필요할 수 있음. 제품/자체 운영 채택 및 실제 설정은 HOLD |

[CP0059 관측](step-4b-support-readonly-evidence.md)에 `profiles.id → auth.users` 삭제 cascade, profiles/admin_permissions/join_requests 및 선택 RPC 경로가 있어 Auth를 바꾸면 단순 game-local 작업으로 끝나지 않는다. [정적 signOut](https://github.com/limbit95/limbit95.github.io/blob/5d2424405410696db4afd44d439d9a5210f04f80/js/auth.js)은 범위 없는 호출이다. 이 사실은 운영 전체 의존성 감사가 아니며 실제 적용/모든 writer 불변을 보증하지 않는다.

**사이트 managed Auth를 유지한 채 vNext만 자체 session으로 격리**하는 안에는 두 문제가 남는다. ① 기존 Auth R가 vNext를 즉시 철회하는 의무를 유지하면 원래 문제가 남는다. ② 그 연결을 없애면 사용자 정책 변경이다. 따라서 현 요구의 자동 충족안으로 채택하지 않는다. 반대로 사이트 Auth 전체 교체가 기존 게임 DB/RPC·로그인 소비자의 변경을 요구하면 기존 게임 무이관 조건과 충돌할 수 있다. 변경 없는 호환 Adapter로 의미를 유지하는 증거가 없으면 그 방안도 채택 HOLD다. “분리”라는 이름으로 문제를 숨기지 않는다.

## 모든 철회 경로의 처리 조건

| R 경로 | 대안의 필수 통제 | 부족하면 |
|---|---|---|
| 승인·가입·role·permission | API/RPC/trigger/직접 SQL 모두 통제된 권위 변경 순서에 참여. 우회 writer는 보호 개방 중 사용 불가능한 권한/운영 경계 필요 | 단순 운영자 주의사항만으로 충족 금지. 보호 서비스 닫힘/HOLD |
| default/global/local/others | 현재/전체/현재 제외 session과 동시 생성/refresh cut를 같은 권위 계층에서 집행 | 앱 wrapper만으로 managed 직접 API를 막았다고 주장 금지 |
| 직접 Auth API·console·계정 삭제 | 실제 효력 이전 차단 경로에 참여하거나 대상 권위 경계를 직접 통제하는 구조로 변경 | 기존 managed 경로가 남으면 대안 미완성. 감지 후 일시정지는 즉시 철회 증거 아님 |
| JWT/session 만료 | 실제 deadline까지 final C/P 차단, pause와 queue에도 유효 | exp가 지나도록 오래된 permit 사용 금지. 자동 clock check만으로 완료 선언 금지 |
| owner 교체·복원 | old 저장/외부 C/egress 차단 각각 증명, 새로운 incarnation과 현재 권한 확인 | DB epoch만 증가시켜 개방 금지 |

R은 기존 실제 효력이며 감지·앱 통지 시점으로 이동하지 않는다. C는 실제 권위 반영, P는 recipient/session/view/payload의 실제 최종 제공이다. R 전에 검증된 P의 늦은 도착은 이미 제공된 정보와 구분하되 app/SDK/TLS/OS queue·socket.write·proxy·실제 egress·transport 재전송을 혼합하지 않는다. 권한 불명 시 즉시 보호 입력/정보 차단→해당 판 pause→최초 장애60초 내 복구 실패 abort를 유지하며 60초는 grace가 아니다.

## 변경 영향과 사용자 결정

이 대안은 게임 서버료만 비교하는 변경보다 운영 책임이 커질 수 있다. Auth/권한 집행·송신 차단·패치/장애 대응·복원 현재성 검증의 책임과 비용이 추가된다. 기존 Free 서울 DB 유지 후보와 **전체 추가비 세금 포함30,000원** 동시 충족은 미검증이다. 평일20~24/주말“풀”의 현재 대응 정보를24/7로 확대하지 않는다. 기능이 줄거나 품질 기준이 완화된 후보를 통과시킬 수 없다. 비용/운영/단말/백업 명세는 재작성하지 않는다.

| 사용자 결정이 실제 필요한 범위 | 선택지 | 추천/이유·승인 상한 |
|---|---|---|
| 최종 채택 시 Auth/권한 운영 경계 변경을 수용할지 | 목표를 유지한 통제 경계 변경을 수용 / 현재 managed Auth 경계를 고정 | **조건이 증명된 통제 경계 변경 수용을 추천.** 그러나 실제 변경 범위·기존 게임 무변경·전체 비용/운영 증거가 아직 없어 지금 제품 교체 승인으로 요청하지 않는다. 이번 “진행”은 대안 판단만 허용한 것으로 기록 |

현재로서는 새 사용자 정책 승인을 받아 즉시 해결되는 상황이 아니다. 설계 담당은 기존 게임 무변경·모든 R·실제 egress·expiry·비용/운영을 만족하는 구체 배치가 제시되기 전에는 “Auth 변경 허용”만 받아 채택 처리할 수 없다. 기술 알고리즘을 사용자에게 선택시키지 않는다.

## 다음 작업과 STEP4B 종료 조건

**이번 대안 수용 심사는 채택 HOLD로 종료한다.** 조건1은 managed R가 남는 격리안에서 충족되지 않고, 전체 통제안에는 사이트 경계 변경이 필요하다. 조건2는 구체 최종 egress/expiry 집행 primitive가 미선택이다. 조건3의 기존 게임 무변경 호환과 조건4의 전체 비용/성능 증거도 없다. 따라서 다음 작업을 동일한 대안 판단 문서 재작성으로 지정하지 않는다. 아래 네 조건은 실제 채택 재검토의 기준이다. 구체 제품/배치가 주어진 후 재검토한다.

1. 모든 사이트/Auth R 경로가 통제된 집행에 참여하며, 기존 Auth R 의미/만료 deadline을 바꾸지 않는다.
2. actual C/egress·old owner·expiry를 강제 차단할 구체 배치/지원 primitive가 있다. app permit/DB lock/socket 반환으로 대신하지 않는다.
3. 기존 게임 이관·권한/로그인 의미 변경 없이 사이트 연결 경계를 수용할 수 있다. 불가이면 영향도 충돌을 명시한다.
4. 전체비용30,000원·100명/판8·p95 250ms·개별 재연결5초·모바일·기존 복구/삭제·운영 대응 목표와 양립할 검증 경로가 있다.

하나라도 해법 없이 빠지면 **이 대안을 채택할 수 없다고 결론**낸다. 이름만 바꾼 다음 후보/준비 문서를 반복하지 않는다. 그 경우 사용자에게 제시할 것은 요구와 고정 구성의 구체 충돌이며, 요구 완화는 자동 진행하지 않는다. 현재 문서의 필요조건 제시는 이 네 조건 충족 증거가 아니다.

## 이력과 유지 범위

문의 시도는 공식 화면 열기 timeout으로 끝났으며 문의 본문 전송/접수번호를 확인하지 못했다. 공급자의 거절·비지원·답변으로 취급하지 않는다. 이번에는 재시도·문의 전송·운영 SQL/권한 변경 없음. CP0064의 문의 우선 순서는 현재 추천에서 대체됐으나 당시 판단/질문 초안은 보존한다. 구조/제품/정책 미채택이므로 DECISIONS 변경 없음.

총접속100명·판8명·세금 포함 월추가30,000원·p95반응250ms·정상망 회복 재연결 각5초·모바일 이동/상호작용/준비/종료/재접속, 권한 불명 즉시 차단/판 pause/최초60초중단, 본인 참가/필요 운영자 열람·최초 권위종결+30일 삭제·탈퇴 식별 연결 제거, 하루1회 외부/RPO24h·발견 후24h 수동 복구·최근7일 복구점/삭제 우선을 유지한다. 사용량/미래 기존소비/실청구 UNKNOWN이며 RPO는 과거 권한 부활 허용이 아니다.
