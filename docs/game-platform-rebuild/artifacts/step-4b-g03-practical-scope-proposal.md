## 쉽게 보는 추천안

권한 보호는 유지하되 설계 승인과 오픈 전 시험을 분리한다. 외부에서 실제로 철회된 순간과 게임 서버의 최종 네트워크 송신을 완전히 동시에 묶는 기존 보장은 아래의 제한된 지연 후보로 변경 검토한다. 이는 단순 설명 정리가 아니라 보장 범위의 변경이다.

| 구분 | 기존 요구 | 추천 후보 / 사용자에게 달라지는 점 |
|---|---|---|
| 단계 | 실행 증거 미확보가 G03 전체 blocker | 설계 적합성과 실제 지원을 별도 상태로 추적. 모순 없는 구체 구조/시험 계획이면 설계만 승인 가능; 오픈은 실행 증거 있어야 함 |
| 사이트 내부 승인/운영권한 | R 이후 불허 C/P 0 | 통제 가능한 권한 변경과 보호 mutation은 같은 권위 DB 순서로 판정. 철회 후 새 행동 거절 유지 |
| 외부 Auth/API/console 철회 | 실제 R 직후 불허 C/P 0 | 대상 session마다 실제 R부터 **최대5초 이내** 권위 행동 반영과 새 정보 제공 차단. 그 구간의 제한된 잔여 접근 가능성을 승인해야 함 |

| 권한 확인 실패 | 즉시 deny → 판 pause → 최초 장애60초 abort | 유지. 확인 실패를 안 뒤 5초 더 허용하는 것이 아님 |

5초는 추천 정책 후보이며 Supabase의 SLA·측정값·승인값이 아니다. 재연결5초와 별개다. 1초 polling 같은 주기/알고리즘도 자동 채택하지 않는다. 후보 승인 전 기존 A안 안전성 요구가 유효하고 G03 OPEN/BLOCKING 그대로다. 과거 판단을 오판 이력으로 재작성하지 않는다.

## 반드시 유지할 기본 보호

- 본인/허용 recipient·view만 정보 제공. 타인 종료 기록·숨겨진 패/역할·운영자 정보는 무권한 접근 차단. 브라우저 state/UI 숨김만으로 인가하지 않는다.
- DB/RPC/Data API 우회를 포함해 보호 입력마다 현재 승인/역할/대상/owner 확인. 중복 command는 mutation 재반영하지 않고 응답은 새 정보 인가 적용.
- snapshot 생성은 송신 허가가 아니다. 최종 recipient/session/view/payload 재검증, view 변경·늦은 callback·dispose/재연결 경로 점검.
- 권한 확인 실패·stale 허가의 허용기한 만료는 닫힌 상태. 대상 판 pause, 최초 실패 deadline60초 유지. 정상망 회복 후 각 재연결5초는 별도 조건.
- known JWT 만료는 deadline. 그 시각 이후 새 허용 토큰/검증 없이 보호 연산을 진행하지 않는다. 외부 session timeout·삭제·global/local/others 대상은 별도 검증하며 session row 존재만으로 모든 만료를 판정하지 않는다.
- old owner는 DB 저장과 앱 송신 둘 다 차단. 복원은 격리/새 incarnation/현재 권한·삭제 검증 후 개방. RPO24h는 철회된 권한 부활 허용 아님.

타인 정보에 애초부터 권한이 없는 경우를 “5초 허용”으로 해석하지 않는다. 허용은 이전에 유효했던 대상의 철회 전파 지연만 해당한다. 새 결제/금전/중요 운영 변경 같은 더 민감한 기능까지 같은 정책으로 승인하지 않는다.

## 기술 방향과 정확한 한계

추천 방향은 기존 사이트·게임 Auth 유지, vNext의 DB 우선 명령 처리와 통제된 송신 gateway다. 기존 게임 무이관/소비자 격리 유지. DB allow 뒤 멈췄다가 무기한 apply/send하는 구조를 채택하지 않는다.

외부 철회 지연 상한을 보장하려면 검증 성공의 신선도 기한, 조회 지연/clock 오차 여유, 외부 철회의 관측 가능성, process pause 후 재개 때 재검증, queue에서의 재검증이 함께 필요하다. 검증 **완료 시각**만으로 허용기한을 새로 시작하면 이전 snapshot의 늦은 조회로 상한을 넘길 수 있다. 판정 원천/읽기 순서와 최대 관측 지연을 명시해야 한다.

정책 후보에서조차 권한 check와 최종 반영/인계의 틈은 사라지지 않는다. 제한된 잔여 지연을 허용하는 의미다. 5초 상한을 증명할 수 없는 구현·환경은 실패이며 “대부분5초”로 합격하지 않는다. 실제 R 시각/인계 경계가 관측 불가하면 INCONCLUSIVE/HOLD. transport가 자체 queue를 제공한다면 인계 위치/취소 불가 범위를 명시하고 app queue 추가는 최종 경계로 속이지 않는다.

이 방향은 기존의 무지연·actual-egress 계약을 충족한다고 주장하는 구조가 아니다. 사용자 승인 후 변경된 요구에 대해 새 설계 적합성을 판정한다. 무료 플랜·100명·품질·비용과 양립 여부는 아직 미검증이다. 상한이 부담스러우면 숫자를 자동 늘리지 말고 변경안/충돌을 보고한다.
