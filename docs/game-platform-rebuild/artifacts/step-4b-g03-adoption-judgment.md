# STEP4B — G03 채택 가능성 판정 (CP0064)

2026-10-06 KST. 고정 입력 CP0063 `404606f773c826e4de4c4dd05fb04c5347557638`, 시작 PR412 HEAD 일치/추가 변경 0. [집중 근거](step-4b-g03-focused-support-evidence.md) F63-01~12/U63/M63-01~05 및 [CP0062 J62-01](step-4b-operations-design-judgment.md)을 입력으로 한다. 이번은 Astra 성격의 설계 판단이며 별도 모델/독립 감사 실행 인증은 아니다.

## 1. 최상위 판정과 추천

**B — 현재 후보는 필수 지원 사실 미확보로 채택 HOLD.** 현재 후보란 Supabase Free·서울의 managed Auth/사이트 권한 원천을 유지하면서 저빈도 DB 권위와 외부 게임 실행·송신을 연결하는 조합이다. 이 조합에 필요한 모든 R와 최종 C/P의 공동 집행 계약은 확보되지 않았다. 공식적인 전면 비지원이나 모든 대안의 불가능성을 확인한 것은 아니다.

**배제 판정 C는 더 좁은 방식에 적용한다.** 사전 DB allow 뒤 독립 외부 apply/send, 짧은 TTL·refresh·event/cache만으로 철회를 반영하는 방식은 아래 반례를 배제하지 못하므로 현 요구의 충족 구조로 채택할 수 없다. 이 판정은 CP0060/62의 제외를 유지하며 새 정책·제품·알고리즘 채택이 아니다. DECISIONS는 변경하지 않는다.

**추천 다음 경로는 한 가지: §5의 최소 지원 질문을 사용자 승인 후 한 번 문의하고, 답변으로 P1의 계속 검토/배제를 결정한다.** 이 문서에서 실제 문의는 보내지 않는다. 답변 전 같은 Sol 자료 준비나 fingerprint 조회를 반복하지 않는다. 긍정 답변도 곧바로 G03 해소가 아니라 구체적 구조의 증명 가능성을 검토할 진입 조건이다.

## 3. C/P/R와 반례 판정

- **R:** 해당 scope의 권한이 실제로 효력을 잃는 권위 지점. 사이트의 승인/가입/role/permission 변경, 직접 SQL, Auth logout/delete 각각의 실제 효력과 만료 deadline을 따른다. event 도착·앱의 감지·logout 응답 시각으로 임의 이동하지 않는다. 동시 refresh/새 session 생성의 scope 포함 여부도 계약이 필요하다.
- **C:** 외부 권위 상태가 실제 바뀌는 지점. DB 내 완결된 결정을 이후 계산 없이 투영하는 경우 DB commit과 투영을 구분할 수 있으나, 외부 simulation이 physics/random/tick 등의 새 권위 결정을 하면 그 외부 반영이 C다. 명칭 변경으로 이 의무를 제거하지 않는다.
- **P:** 특정 recipient/session/view/payload의 보호 정보가 신뢰한 최종 송신 경계를 실제로 통과하는 지점. app enqueue, SDK/TLS/OS queue, socket.write 반환은 자동으로 P가 아니다. 실제 egress를 어디서 통제·관측할지 제품별로 특정해야 한다. 여러 조각의 payload가 R에 걸치면 R 이후 조각을 사전 인가로 정당화하지 않는다.
- 검증된 P가 R 전에 완료된 데이터의 늦은 도착은 새 P와 구별한다. R 이전 합법 제공 정보의 회수까지 요구하지 않는다. 반면 아직 큐에 있거나 관측되지 않은 데이터를 모두 이전 P라고 간주하지 않는다. transport 재전송·proxy buffering의 경계도 명시되어야 하며 현재는 HOLD다.
- 실제 권위 순서는 commit/차단 완료/egress의 연계 증거로 판단한다. 서로 다른 clock timestamp만으로 순서를 확정하지 않는다. 관측 누락은 INCONCLUSIVE/HOLD이며 안전성 위반을 percentile로 허용하지 않는다.

**배제 증명:** allow 직후 외부 process가 멈춘다. DB 연결/잠금이 소실되고 R이 효력을 얻는다. process가 재개해 이전 allow로 C/P를 수행하면 위반이다. 확인을 한 번 더 해도 마지막 check와 effect 사이에 같은 중단을 넣을 수 있다. R 이벤트가 지연된 실행과 R이 없는 실행이 sender에게 동일하게 보이는 동안 계속 보내는 event-only 구조도 안전성을 증명하지 못한다. 따라서 외부 effect를 실제 차단하는 주체가 현재 R/owner와 결합되어야 한다. 이 논증은 특정 지원 계약이 없는 독립 check→effect에 한정한다.

| 경로 | 필요한 권위 조건 | 판정/실행 의무 |
|---|---|---|
| 승인·가입·role·permission·직접 SQL | 모든 변경 writer가 같은 철회/최종 차단 계약에 참여하거나 보호 서비스 개방 중 우회가 불가능해야 함 | 선택 함수 12개로 충분하지 않음. privileged SQL·배포·RLS bypass 포함 writer 통제 증거 필요 |
| global/local/others·직접 API·console/계정 삭제 | scope별 session의 실제 R과 final C/P fence가 결합되어야 함 | wrapper만 통제하면 직접 경로가 남음. managed 내부 writer 지원 계약 미확보 |
| session/JWT 만료 | 최종 effect 시점의 deadline 유효성, clock 오차/지연/긴 pause 처리 | row 존재·transaction 시작 시각만으로 판정 금지. Free에 유료 timeout 가정 금지 |
| snapshot/view 교체 | cut 이후에도 recipient/session/view/revision에 맞는 최종 P 인가 | 늦은 callback·queue·retry·error 등 모든 완료 경로 포함 T02/T05 |
| commit 후 ack 유실·duplicate | C의 dedupe와 새로운 응답 P는 독립. 저장 결과의 존재가 열람 권한 아님 | R 뒤 private duplicate 응답 금지. 최소 오류에도 비밀 payload 포함 금지, T04 |
| old/new owner | 저장 CAS/epoch와 외부 C/P 차단을 각각 집행. 차단되지 않은 old owner가 있으면 새 보호 실행 개방 금지 | DB 저장 deny와 old owner egress 0의 독립 trace, T08 |
| 복원 | 격리 상태·새 incarnation·옛 credentials/session/owner 무효화와 현재 권한 재확인 | DB와 함께 rollback되는 epoch/권한/삭제 원천을 현재성 증거로 사용 금지. 실패 시 닫힘 유지, 기존 B05/06 연결 |

## 4. 필요한 범위의 후보 비교

| 후보 | 모든 R / 최종 C·P·owner 경계 | 사실·미확인과 이전 판단 차이 | 판정·추천 및 실행 의무 |
|---|---|---|---|
| P0: 사전 조회 + 외부 server 송신 | 조회된 권한을 외부 process가 나중에 사용. R/잠금 소실이 최종 effect를 막지 않음 | API/DB 수단은 존재하지만 그 사이 반례가 남음. 기존 배제 유지 | **C, 배제.** 두 번 조회·TTL/event로 재포장하지 않음 |
| P1: managed R 참여 + 권위 집행/최종 송신 차단을 연결 | DB는 완결 가능한 C를 소유. 외부 권위 C는 같은 순서에 참여. 별도 최종 송신 주체가 session/view/payload/owner를 검증하고 실제 egress를 차단. 모든 R writer는 차단과 결합하며 우회 금지 | 저빈도 DB 방향 유지. 차단 완료 전에 독립 R이 효력을 얻는 경로가 있으면 실패. DB lease/읽기 성공만으로 최종 송신 주체를 구현했다고 간주하지 않음. **해당 지원 계약과 구체적 제품은 미확보** | **B, 지원 계약 확인 경로를 추천.** 만료는 지연시킬 수 없으므로 deadline 전 차단 증명이 추가 필요. crash/partition/pause·queue·owner 경합 실행 증거 필수 |
| P2: Auth/권한 writer부터 최종 집행까지 직접 통제하는 대체 구조 | 철회 처리와 C/P를 같은 권위 집행 계층에 넣고 독립 writer/egress를 제거하는 대안. expiry·restore도 그 경계에 참여 | managed Auth를 그대로 둔 채 앱 token만 추가하면 기존 R 우회가 남아 해결 아님. Auth 운영/통합 범위가 바뀌며 현재 Free·서울 조합의 충족안이 아님 | **현 범위 채택 HOLD, P1 명시적 불가 시 재설계 대안.** 자기 운영도 OS/egress·장애 fence를 자동 해결하지 않음. 실제 지원 구조·운영/총비용/품질 재검토와 별도 변경 결정 필요 |

P1은 구현 가능한 완성 알고리즘의 채택이 아니라 필요한 계약의 구조다. 특히 “gateway가 매번 DB를 조회한다”는 것만으로 P1이 되지 않는다. R 이전에 fence가 성립한다는 증거 또는 같은 최종 권위 순서에서 R/C/P가 집행된다는 계약이 필요하다. 실제 managed R을 앱에서 뒤늦게 효력이 생긴 것으로 재정의하지 않는다. 만료 지연·인가 유예·G03 기존 A안에서 B안으로의 전환은 제안하지 않는다. 위 최상위 분류 B는 사용자 지정 판정 이름이며 과거 안전성 B안과 다르다.

## 5. 판정을 바꿀 최소 부족 증거와 문의 초안

**먼저 Q64-1을 판단한다.** Q64-2가 긍정이어도 Q64-1을 대신할 수 없다. 공급자가 외부 게임 전체를 인증해 줄 것이라고 가정하지 않고 managed 측 참여 계약과 책임 경계만 묻는다.

1. **Q64-1 — 모든 managed R의 참여 계약:** Free·서울에서 global/local/others logout, 직접 Auth API, console/계정 삭제의 실제 철회 효력이 외부 최종 C/P 차단과 같은 순서에 참여하도록 하는 공식 지원 lock/hook/protocol이 있습니까? 각 경로·동시 새 session/refresh·장애/DB 연결 소실·버전 변경의 보장과 우회 경로를 특정해 주십시오. 만료는 지연할 수 없으므로 만료 판정/강제 종료와의 경계도 알려주십시오. 없다면 명시적 비지원과 단순 미문서화를 구분해 주십시오.
2. **Q64-2 — 현재 session 판정 계약:** 지원되는 최소권한 API/DB 방식으로 현재 session의 scope별 철회·사용자 삭제·JWT/session 만료를 무엇까지 확인할 수 있습니까? 적용 Auth 버전/SDK 식별 방법, session_id 없는 token, 오류·일시 조회 장애의 의미를 명시해 주십시오. 조회 성공 이후 외부 C/P까지 인가를 보증하는지 여부는 별도로 답해 주십시오.

비밀키·token·비밀번호·실사용자 데이터 첨부 없이 보내는 초안이다. **이번 미전송.** 유료 지원 가입/구매도 승인된 것이 아니다.

| 필요한 증거/담당 | 답변 또는 자료별 판정 변화 | 종료 조건 |
|---|---|---|
| Q64-1 공급자 공식 답변, M63-02 | 구체적 참여 계약 있음 → P1의 end-to-end 설계 증명 검토. event/TTL/사전 조회만 제시 → 필요 계약 충족 아님. 필수 경로 명시적 불가 → 현 P1 배제 후 P2 구조 변경 검토. 미답변/미문서화 → B 유지 | 관련 경로별 문서/답변일·버전·실패 의미를 한 번 수용표에 대조. 같은 검색 반복 종료 |
| Q64-2 공급자/운영 버전 자료, M63-01 | 현재 predicate 범위 확인에 사용. 모든 조회 조건이 확인돼도 final C/P 문제는 남음 | 운영 버전 적용 근거와 최소권한/만료 조건이 구체적이어야 함 |
| 운영 writer와 최종 sink 명세, M63-03/04 | P1의 지원 계약이 확보된 뒤 설계 담당이 해당 계약의 모든 writer·runtime/transport 경계를 실제 구성에 대입 | 빠진 writer·독립 socket·rollback 원천이 있으면 채택 HOLD. 반복 fingerprint는 대체 증거 아님 |
| 실행 trace, M63-05 | 구조 채택 검토와 별도. 모든 R 후 불허 C/P 0, 저장/송신 fence·만료·복원 경합 증명 | 별도 허용 단계 T01~05/T08/T10 및 관련 B. NOT_RUN 상태로 통과 선언 금지 |

답변 전 가능한 일은 이 판정의 검토와 문의 전송 여부 결정이다. 보호 adapter 구현·제품 구매·게이트 해소·다음 STEP 착수는 중단한다. 미답변 기간을 자동 채택/요구 완화 근거로 사용하지 않는다. 사용자가 문의를 보류하면 외부 의존 대기 상태를 유지하며 추가 자료 문서를 자동 생성하지 않는다.

## 6. 사용자 결정과 STEP4B 종료 경로

이번에 새로 필요한 사용자 결정은 **지원 질문 전송 여부 한 가지**다. 기술 구조 선택은 설계 담당 책임이다.

| 우선순위 | 선택지 | 추천·이유 |
|---|---|---|

STEP4B 종료까지 필요한 일은 다음 순서로 한정한다.

1. **G03 지원 가능 경로 판정:** Q64-1/2 답변을 P1에 대입하거나 명시적 불가를 확인해 대체 구조를 판단한다. 미답변이면 외부 의존 HOLD이며 같은 수집을 반복하지 않는다.
2. **선택 구조의 공백 해소:** 모든 R·최종 C/P·owner·복원 권한의 책임/지원 계약/관측 가능성을 확정한다. G01/02/04/05에는 달라진 영향만 연결한다. 미확인을 후속 작업으로 이름만 옮겨 완료 처리하지 않는다.
3. **필수 검증과 완료 심사:** 문서로 결정 가능한 항목과 사전 실행 증거가 필요한 항목을 명시한다. 필요한 실행이 현재 허용 범위 밖이면 별도 범위 허용이 있어야 하며, STEP6 전 공통 runtime 금지와 충돌하면 계획 수준에서 명시적으로 검토한다. 이번에 시험·계획 변경을 허용하거나 뒤 단계로 자동 이관하지 않는다. 실행 증거가 필요한 열린 게이트를 문서만으로 해소하지 않는다.
4. **정식 산출물 정합화·검토/병합 승인:** 위 조건 충족 후 별도 지시로 진행한다. 전체 STEP4B 완료, PR integration 병합, STEP5A 시작은 각각 별도이며 이번에는 모두 수행하지 않는다.

완료 날짜는 외부 답변·선택 구조·필수 증거 확보에 달려 있어 산정하지 않는다. 이번 진척은 **배제할 방식과 판정을 바꿀 단일 외부 의존을 확정하고 반복 수집을 종료한 것**이다.
