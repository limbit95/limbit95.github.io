# STEP4B — 사용자 결정 질문

**상태: 전 질문 UNANSWERED. 추천은 제안이며 선택·승인·게이트 해소가 아니다.** [요구 검토](step-4b-requirements-review.md)를 기준으로 작성했다. 먼저 Q01/Q05/Q06에서 실제 검증할 경험·규칙 범위를 정하고, Q02~04/Q07에서 규모·환경·운영·복구 조건을 채운다. 모르는 숫자는 공란/미정으로 답해도 된다. 미정이면 관련 기술 선택을 보류하거나 별도 추정 근거를 마련한다.

## 우선순위 1 — 무엇을 검증하고 어떤 규칙을 적용할지

### Q01. 첫 2D 협동 Probe에서 어떤 조작 경험을 검증할까요? — G01

작은 2D 협동이라는 계획은 유지한다. 세부 게임 기획 전체나 엔진 선택을 지금 확정하라는 질문은 아니다.

| 선택지 | 의미/영향 |
|---|---|
| A 이동과 상호작용 중심 협동 — 추천 | 함께 이동하고 장치를 조작하거나 목표를 달성. 연속 입력/공유 상태·이탈/재연결을 다루면서 정밀 전투 판정 부담을 제한할 수 있음 |
| B 빠른 회피·액션 중심 협동 | 반응 속도가 경험에 더 중요해져 지연/보정·입력 판정 검증 요구가 커짐 |
| C 다른 구체 경험 또는 아직 미정 | 원하는 동작을 말로 설명. 이를 보고 필요한 지표를 제안하며 장르/수치를 대신 확정하지 않음 |

**추천 이유:** 첫 Probe의 목적은 실제 다중 client·권한·수명/복구 검증이다. A가 그 목표에 집중하기 쉽다. A를 골라도 느려도 된다는 뜻은 아니며 허용 지연은 후속 측정 기준으로 따로 정한다. 계획의 실제 실시간 전달 요구를 mock/턴제로 대체하지 않는다.

답변: `Q01 = A/B/C, 꼭 포함할 동작 = ___, 특히 불편하면 안 되는 순간 = ___`

### Q05. 첫 온라인 Probe의 “다시 플레이” 흐름은 어떻게 할까요? — G06

여기서 방장은 시작 버튼을 누르는 사용자 역할이다. 서버 권위와는 다른 개념이다. 방장을 없애도 신뢰 서버의 판정 책임은 남는다.

| 선택지 | 의미/영향 |
|---|---|
| A 기존 참여 맥락 유지·재참여 의사/준비 확인 후 방장 시작 — 추천 | 현행 재대결 의무와 충돌을 줄여 첫 실시간 모델 검증에 집중. 방장 이탈/승계도 서버에서 처리해야 함 |
| B 모두 재참여를 확인하면 서버가 시작, 사용자 방장은 없음 | 원하는 경험이 이 방식이면 검토 가능. 현행 §10B와의 적용 범위/독립 장르 정책·상위 변경 승인 검토 필요 |
| C 경기별 자동 매칭/별도 재시도 또는 미정 | 기존 참여 맥락·명시적 의사·재대결 의무와 무엇이 달라지는지 먼저 분석해야 함 |

**추천 이유:** A는 첫 Probe에서 불필요한 규칙 변경 범위를 줄인다. 모든 미래 게임에 방장을 강제하자는 추천은 아니다. B/C 선택도 즉시 규칙 변경 승인이나 면제가 되지 않는다. 기존/신규 보드게임의 해당 의무는 보존한다.

답변: `Q05 = A/B/C, 종료 후 기대 흐름 = ___`

### Q06. 두 번째 방·host 없는 Probe는 어느 쪽을 우선할까요? — G06·G04

계획이 허용한 두 갈래 중 우선 검증할 제약을 좁힌다. 게임 구현/STEP9B 착수는 이번 범위가 아니다.

| 선택지 | 의미/영향 |
|---|---|
| A 서버 기록/보상 연동 없는 로컬 단독 플레이 — 추천 | 가짜 Room/host 없이 같은 플랫폼 진입·수명·종료가 작동하는지 집중 검증. 저장이 필요하면 로컬 보존 범위는 따로 명시 |
| B 서버에 진행/기록을 남기는 비동기·기록형 | 장기 상태·계정 권한·중복 저장·복구/보존까지 함께 검증. 다른 사용자와 상태를 공유하는지도 추가 확인 필요 |
| C 아직 미정 | 장기 목표를 설명하고 선택 유지. 이 분기 관련 G01/G04/G06의 적용 범위는 열어둠 |

**추천 이유:** A는 첫 온라인 Probe와 대비되는 “선택 기능이 없어도 성립하는 실행”을 확인하기 쉽다. B가 당장 제품 목표에 필요하면 B가 더 적합할 수 있다. 로컬 결과를 나중에 보호된 서버 기록으로 올리는 기능은 A에 자동 포함되지 않는다.

답변: `Q06 = A/B/C, 계정 간 기록/진행 공유 필요 = ___, 다른 사용자와 상호작용 = ___`

## 우선순위 2 — 규모·환경·운영 목표

### Q02. 첫 검증은 어떤 이용 범위와 규모를 목표로 할까요? — G01·G05

| 선택지 | 의미/영향 |
|---|---|
| A 제한된 초대 시험의 목표부터 정하기 — 추천 | 계획의 제한적 Probe에 맞춰 시험 참여자/동시 접속/판 규모를 구분. 추후 공개 목표는 별도 기준으로 확장 |
| B 제한 시험과 향후 확대 목표를 함께 지정 | 설계 비교에 두 workload를 사용하되 이번 공개/출시 승인으로 취급하지 않음 |
| C 이용 규모 자료부터 확인 | 아직 예상이 없으면 현재 모집 가능 인원·사용 패턴 등 근거를 먼저 모음. 단일 추측값을 확정하지 않음 |

**추천 이유:** A는 지금 검증할 범위를 구체화하면서 미래 목표를 실제 지원 수치로 오인하지 않게 한다. A여도 아래 숫자가 필요하며 추천 자체에 인원 기본값은 없다.

답변: `Q02 = A/B/C, 전체 시험 참여 예상 = ___명, 같은 시간 게임 접속 목표 = ___명, 한 판 인원 = ___명, 동시 진행 판 수 = ___, 관전자 포함 여부/예상 = ___`

계획의 2클라이언트 검증은 최소 증거다. 방 정원·서비스 동접을 2로 확정하지 않는다. 서로 맞지 않는 숫자가 오면 Work가 이유를 확인하고 workload를 다시 제안한다.

### Q03. 어떤 기기·지역·접속 환경을 먼저 보장해야 할까요? — G01·G02·G05

| 선택지 | 의미/영향 |
|---|---|
| A 실제 시험자에게 가장 많은 한 기기군/지역부터 — 추천 | 대표 단말·브라우저·회선을 사용자가 지정. 우선 기준 밖 환경은 미검증으로 남김 |
| B PC와 모바일을 첫 검증부터 모두 포함 | 조작/화면뿐 아니라 백그라운드·복귀·네트워크 차이도 검증 범위에 포함 |
| C 여러 국가/기기군을 첫 단계부터 포함 | 지역별 지연·가용성·운영비 비교 범위가 커짐. 실제 대상과 우선순위 필요 |

**추천 이유:** A는 제한 시험의 합격 기준을 좁혀 관찰하기 쉽다. 사용자가 PC/국내만 쓴다고 가정하지 않는다. 휴대폰 참여가 필수라면 B가 맞으며 임의로 제외하지 않는다.

답변: `Q03 = A/B/C, 필수 기기/브라우저 = ___, 참여 지역 = ___, 주 회선(Wi-Fi/모바일 등) = ___, 꼭 지원할 복귀 상황 = ___`

### Q04. 비용과 운영 부담은 어디까지 허용할까요? — G01·G05

| 선택지 | 의미/영향 |
|---|---|
| A 추가 월비용 상한 안에서 관리 부담을 줄이는 방향 — 추천 | 관리형 서비스도 후보에 넣되 실제 총견적/보안/복구 검토 후 선택. 공급자 선택은 미정 |
| B 지출을 최대한 줄이고 직접 운영 부담을 감수 | 서버 갱신·배포·감시·백업·장애 대응을 맡을 시간/담당자를 확인해야 함. self-host가 더 싸다고 미리 단정하지 않음 |
| C 추가 유료 지출 불가 또는 아직 예산 미정 | 유료 지출 불가라면 요구와 맞는 후보 존재 여부부터 확인. 불가능하면 범위 조정/보류를 제안하며 요구 충족을 약속하지 않음 |

**추천 이유:** A는 게임 개발 외 운영에 쓸 수 있는 시간이 제한될 경우 비교 출발점으로 적절하다. 사용자의 운영 여건은 아직 확인되지 않았으므로 B가 나쁜 선택이라는 뜻은 아니다. 현재 가격표나 특정 상품 구매 추천이 아니다.

답변: `Q04 = A/B/C, 이번 게임용 추가 월상한 = ___원 또는 미정, 기존 사이트 비용 포함/별도 = ___, 필요한 가동 시간 = ___, 장애 대응 가능한 시간/담당 = ___`

정확한 예산이 어렵다면 “유료 가능하지만 견적을 보고 결정”으로 답할 수 있다. Work가 임의 금액을 상한으로 쓰지 않는다. 자동 상한 차단·중단 조건이 필요한지도 후속 견적에서 확인한다.

## 우선순위 3 — 장애 때 지킬 경험과 데이터

### Q07. 연결/서버 장애 때 어디까지 이어서 플레이해야 할까요? — G01·G02·G04

단순 인터넷 끊김과 권위 서버 crash를 구분한다. 어느 선택도 확정 결과·장기 진행을 임의 소실하거나 미승인 데이터를 노출하는 허가가 아니다.

| 선택지 | 의미/영향 |
|---|---|
| A 일시 단절은 현재 상태 복원, 서버 crash면 해당 미완료 판 중단 가능 — 첫 제한 Probe 추천 | 판 중단을 명시하고 재시도 흐름 제공. crash를 정상 완료로 기록하지 않음. 확정/영속 상태의 보존 약속은 별도 유지 |
| B 서버 crash 뒤에도 진행 중 판을 이어갈 필요 | 중간 상태 저장·복구·owner fencing과 비용/복구 목표를 더 구체화해야 함 |
| C 경험을 더 논의한 뒤 결정 | 잃으면 안 되는 것과 기다릴 수 있는 범위를 먼저 정리. G04 보류 유지 |

**추천 이유:** A는 첫 제한 Probe의 실제 단절 복원 검증을 유지하면서 서버 crash 후 경기 연속성의 추가 범위를 제한한다. 사업/게임 경험에 중단이 허용되지 않으면 B를 선택해야 한다. A도 실제 구현/검증 전 지원 완료가 아니다.

답변: `Q07 = A/B/C, 단절 시 기다릴 수 있는 범위 = ___, 서버 장애 뒤 재개까지 허용 시간 = ___, 반드시 남겨야 할 데이터 = ___, 잃어도 되는 미확정 진행이 있다면 = ___`

## 답변 이후의 흐름

Work가 답변을 결정 기록 초안으로 정리하고 모호한 값/상충 요구를 확인한다. 그 다음에 G01 수치·측정기준, G06 적용성/변경 필요, G02~05 기술 대안·공식 근거·비용/보안/복구 방법을 구체화한다. 사용자에게 RTT/tick/SDK를 근거 없이 고르도록 맡기지 않는다. 답변이 없거나 미정이면 해당 항목을 열린 상태로 둔다.

이번 제출은 질문 준비까지이며 모든 질문의 답변 상태는 UNANSWERED다. 추천안 자동 채택·G01~06 종료·구현·STEP5A·병합·main 반영은 하지 않는다.
